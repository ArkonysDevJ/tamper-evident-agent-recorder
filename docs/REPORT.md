## 2. What VERIFIED_ANCHORED means

`VERIFIED_ANCHORED 0..k` means that the prefix 0..k is backed by a verified RFC 3161 token whose signed
`TSTInfo.genTime` is the TSA’s asserted time for that token (Blueprint §3.3 item 3). It does not mean that each
event existed at its own `ts`; coverage is cumulative. The real receipts of the frozen fixture carry no
`accuracy`, so the receipt-derived bound is reported as **accuracy unspecified**; no policy value is imported.

## 3. Deleted packages versus corrupt evidence

Deleting anchor packages reduces coverage to `VALID_UNANCHORED` for the rows they covered; when the log still
carries the matching `checkpoint_anchored`, the verifier prints `ANCHOR_EVIDENCE_MISSING <k>` and exits 0 (row X1
above). Corrupt, mismatched or invalid evidence is a hard failure with a non-zero exit, never a silent
degradation (rows T1–T6a above, and the Step 2 vectors of spec 003).

## 5. One host: what was built and what was run

All tests ran on one host: 11th Gen Intel(R) Core(TM) i5-11300H @ 3.10GHz × 4, 4 GiB, Linux 6.6.87.2-microsoft-standard-WSL2 (WSL2 on a virtual disk), Node.js v24.22.3, OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13 30 Jan 2024), checkpoint filesystem statfs type 0xef53.

Effective PostgreSQL settings read by the final run: version 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1), server_encoding UTF8, synchronous_commit on, fsync on, full_page_writes on, wal_level replica.

These are the §5.4 deployment invariants (synchronous_commit on for every mutating transaction, fsync on,
full_page_writes on, wal_level replica or logical, UTF8 encoding); the writer reads them before it writes and
refuses to proceed without them. Durability is conditional on the storage stack honoring flush and ordering
requests; on WSL2 that stack is a virtual disk, and no test here measures device behavior under
power loss. Crashes were simulated in three ways, named per case in the test files and in spec 007: an
`fs` double that fails one call (then the writer drains and exits), a real SIGKILL of a child process at an
exact point (E1 barrier, E7, mid-anchor end to end, a tool that ran before its result), and direct SQL edits of
the state row for the defensive states E4 and E5, which a conforming writer never produces.

### Known limits

- Under known limits: the hash covers the canonical block; whitespace in the row envelope (including CR before LF) does not change the verification result.
- Under known limits: the DER order of the SignedData certificate set is not enforced, because the real DigiCert receipts carry that set out of DER order; every other SET OF, including the signed attributes whose DER encoding the signature covers, must be in DER order.
- That the real receipts of the frozen fixture (FreeTSA and DigiCert) carry no `accuracy`, so the reported receipt accuracy is "accuracy unspecified" rather than a policy value.
- Under known limits: a `tool_call` can be recorded whose tool never ran. When the append of record k triggers an anchor and the anchor flow aborts (a namespace mutation fails, the checkpoint transaction fails or has an unknown outcome, or writerConn is lost; §5.7 step 6, §5.3), that append is rejected although row k is committed, and the writer invalidates and exits; a TSA failure never does this (it records `checkpoint_failed` and traffic continues). The log over-reports, never under-reports, and the verifier marks such a call `INCOMPLETE_EXECUTION`.
- Under known limits: an evidence package taken between a crash and the next recovery (for example in E7, with a complete published package whose control was not committed) can show coverage backed by a valid receipt whose `checkpoint_anchored` control is not yet in the log, because §5.3 copies every complete pair and Step 2b does not require a control for a presented package.

### Known debt (Blueprint §10)

- chain_version in genesis ties the genesis hash to a document version; to be decoupled later.
- No independent external record proves that anchor packages existed and were later lost.
- Measuring how reliably agents emit epistemic_pause is outside this sprint.
- Offline TSA certificate revocation is not evaluated; reproducibility is prioritized over live revocation status for the frozen sprint evidence.
- A TSA certificate rotation requires re-pinning the bundle and starting a new chain.
- The ESSCertIDv2 acceptance vector with an explicitly encoded default SHA-256 identifier conflicts with DER and is to be corrected.
- Handling of optional CMS SignedData fields (other CertificateChoices, crls, unsignedAttrs, sid form) is not enumerated beyond ignoring unused embedded certificates.
- Some first-failure placements are not fully pinned: the diagnostic parameter of a row with duplicate seq keys, a later row with seq=0 carrying an application event, and schema checks of anchor.block at Step 2.1 versus 2.6.
- The integer rule is by value: lexical forms such as 10.0 or 1e1 are not distinguished.
- Left to the implementation: transport details per TSA (URL, content type), the commit boundary for epistemic_pause and human_resolution, result_digest when a tool fails, operation literals for application events, arbitrary-precision decoding of Accuracy.seconds and the error code for invalid initializeChain arguments.
- The A1 guarantee assumes complete mediation: every tool call passes through the interceptor.
- pathLenConstraint handling does not state whether a root's own value counts.
- A TSA serving with more than one signer certificate at a time is only partly covered: certificates not pinned in Phase 0 make anchors fail. Phase 0 records whether the retained TSAs' receipts carry crls, unsignedAttrs or other optional SignedData fields.

## 10. Implementation choices (not normative)

Points the Blueprint leaves to the implementation (§10) and readings recorded while building, copied from each
spec.

### Spec 001 — Data core (Blueprint §4 (4.1–4.5), §5.1, §5.2, §5.3 (except the evidence package), §5.3a, §5.4, §6 Step 1 rules 1.1–1.10 (as a)

- **Invalid `initializeChain` arguments** fail with `INITIALIZATION_ARGUMENT_INVALID`, before any SQL mutation.
- **Operation literals for application events:** `tool_call` and `tool_result` use `execute_tool`;
  `agent_final_response` uses `invoke_agent` (OpenTelemetry GenAI `gen_ai.operation.name` values).
  `epistemic_pause` uses `tear.epistemic_pause` and `human_resolution` uses `tear.human_resolution`, since
  OpenTelemetry defines no equivalent.
- **Cut profile selection:** the writer, the recoverer and `initializeChain` take the profile as a required
  explicit option (`base`, `cut1`, `cut1-2`, `cut1-3`, `cut1-4`), fixed for the life of a writer and never
  read from an environment variable.
- **First-failure placements left open (§10):** a row with duplicate `seq` keys is a JSON failure, reported
  as `JCS_SCHEMA_INVALID <expected_seq>`; an application event at seq=0 on a later row fails the §4.4 event
  category rule in Step 1.1, reported as `JCS_SCHEMA_INVALID 0`.
- **Integer rule by value (§10):** integer fields are checked on the parsed number, so `10.0` and `1e1` are
  accepted as 10.

### Spec 002 — Verifier: local chain and output (Blueprint §6 (invocation, exit behavior, Step 1), §6b)

- **Malformed command line:** a missing, repeated or unknown option is an invocation failure:
  `INPUT_UNAVAILABLE 0`, exit 2 (§6b).
- **Exit 3:** an internal error (an unclassified exception) exits 3 with empty stdout and the reason on stderr.
  Exit 3 is outside the §6b contract and is never a successful verification. Before spec 003, inputs that needed
  anchor verification also exited 3; spec 003 implements Steps 2, 2b and 3, so they no longer do.
- **First-failure placements left open (§10):** as recorded in spec 001; the verifier uses the same rule core.
- **Whitespace in the row envelope:** JSON whitespace around a row's object (spaces, tabs, and CR before the LF)
  is accepted, as RFC 8259 permits. The hash covers the canonical block, so this whitespace does not change the
  verification result. Spec 007 lists it as a known limit.

### Spec 003 — Anchoring and the TEAR-TSA-01 profile (Blueprint §5.7, §6 (Step 2, Step 2b, Step 3), §6a, §7 (frozen fixture))

- **Transport per TSA:** HTTP POST of the DER `.tsq` with `Content-Type: application/timestamp-query`
  (RFC 3161 §3.4). Primary `https://freetsa.org/tsr`, secondary `http://timestamp.digicert.com`, in the
  §5.7 order. The URLs were checked on 2026-11-14: both answered a request with a granted response. The response
  `Content-Type` plays no part in acceptance; only the §5.7 step 2 and step 3 checks do.
- **`Accuracy.seconds`:** decoded from its DER INTEGER as a `BigInt`; `ACCURACY_NS` and `LATEST_BOUND_NS`
  are computed in `BigInt`, never through `Number`.
- **DER reader:** the ASN.1 DER reader is written in this repository (`src/asn1/der.ts`). It accepts only
  definite lengths in minimal form and single-byte identifiers, and rejects indefinite lengths, non-minimal
  lengths, high tag numbers, end-of-contents octets, trailing bytes and reads outside bounds, with explicit size
  (1 MiB) and depth (32) limits. It returns elements and byte ranges only; each structure is interpreted in its
  own module. Every hash, signature check and key load uses `node:crypto`. It is tested with negative vectors for
  each rejection rule and checked against `openssl` on every real receipt and certificate
  (`npm run test:local`). It is a trust surface of its own, with no external review.
- **SET OF ordering:** DER order is enforced for every SET OF (signed and unsigned attributes, attribute values,
  `digestAlgorithms`, `signerInfos`, `crls`, and RDNs in Names) except the SignedData certificate set, which the
  real DigiCert receipts carry out of DER order. Because signed attributes must be in DER order, the received
  bytes are their DER encoding, over which the signature is verified as §6a requires.
- **Request encoding:** the SHA-256 AlgorithmIdentifier in the TimeStampReq has absent parameters (RFC 5754 §2),
  since §5.7 step 1 does not fix the form. Both TSAs accepted it.
- **`anchor.block` placement (§10):** Step 2.1 checks `block` only as a JSON object with `seq == k` whose canonical
  hash is `entry_hash`. Its full row schema is checked at Step 2.6, through byte equality with log row k, which
  already passed Step 1.
- **Root `pathLenConstraint` (§10):** a root's own value is not applied; intermediates' values are.
- **Signer keyUsage:** read literally from §6a: when present, it must set at least one of digitalSignature or
  contentCommitment; other bits are allowed ("only" applies to the extendedKeyUsage).
- **ESS binding:** the signer is the embedded certificate that every present ESS reference (v1 and v2) identifies
  by its first certificate hash. `issuerSerial`, when present, must carry the signer serial and a directoryName
  equal to the signer's issuer Name. An explicitly encoded SHA-256 `ESSCertIDv2.hashAlgorithm` is accepted, as §6a
  states, although DER would omit it (known debt in §10). The SignerInfo `sid` must identify the same certificate,
  by issuer and serial or by subjectKeyIdentifier.
- **Signed attributes:** required at Step 2.3; any duplicate attribute type is rejected; content-type and
  message-digest must each carry exactly one value.
- **Optional SignedData fields (§10):** other CertificateChoices, `crls` and `unsignedAttrs` are decoded
  structurally and then ignored. The receipts in the frozen fixture carry none of them (see its manifest).
- **DEFAULT values encoded explicitly:** `ordering FALSE`, an Extension `critical FALSE`, basicConstraints
  `cA FALSE` and certificate version v1 break DER and fail decoding.
- **SubjectPublicKeyInfo:** RSA keys must use rsaEncryption with NULL parameters; EC keys must name P-256, P-384 or
  P-521 by OID.
- **Transport limits:** redirects are not followed; responses over 256 KiB are a TSA failure.
- **`checkpoint_failed.error_type`:** `tsa_unreachable` (timeout or network), `tsa_rejected` (HTTP status or PKIStatus
  not granted) or `tsa_validation_failed` (any other step 3 failure), named after the last retained TSA's failure.
- **Append and its anchor:** the append of record k resolves only after its anchor settled (anchored or
  `checkpoint_failed`). If the anchor flow aborts (filesystem or SQL failure, or writer invalidation), that append
  rejects although row k is committed; the caller treats it as unconfirmed (the tool is not run, nothing is
  delivered).
- **Drain-and-exit:** after a fatal anchor failure the writer invalidates writerConn, waits for started namespace
  mutations, closes writerConn, releases flock and exits the process with code 70. The exit step is injectable.
- **Writer start-up:** a bundle that fails loading stops `ChainWriter.open` with `TSA_BUNDLE_UNLOADABLE`.
- **Frozen fixture with both TSAs:** built once by `npm run fixture:build` through the real writer, export and
  evidence-package steps. For anchors 20 and 40 the primary (FreeTSA) is made to fail locally with HTTP 503,
  without contacting it, so the writer's own fallback obtains real DigiCert receipts; anchors 10 and 30 come from
  FreeTSA. Writer start-up uses the clean-E1 test classifier until spec 006. The tool refuses to overwrite an
  existing fixture.

### Spec 004 — Tamper battery (M1, X1, X2) (Blueprint §7 (M1 matrix, adversary mechanics, acceptance, X1, X2))

- **Runner:** `npm run test:tamper` runs `test/tamper/battery.test.ts` offline. Each case builds an in-memory copy of
  the frozen fixture, applies its exact operation, writes the copy to a temporary directory and runs the offline
  verifier. The frozen files are checked unchanged after the run. The table "specified → measured" is written to
  `test-results/tamper-results.md` (not committed); two runs write the same bytes.
- **Copies:** an unchanged copy serializes to the exact exported bytes; mutated rows are written as canonical
  `{"block":…,"entry_hash":…}` lines. Each case except X1 is checked to change block or `entry_hash` bytes; X1
  leaves `events.jsonl` byte-identical.
- **A2b recomputation:** `prev_hash` and `entry_hash` are recomputed from the first affected row through the tail.
  For T3a and T3b nothing follows the cut, so the A2b copy equals the A2a copy.
- **T4 under A2b:** the inserted row uses `task_id` `inserted-fresh-task`.
- **T6a and T6b receipts:** real receipts, requested once by `npm run tamper:receipts` (network) and stored in
  `test/fixtures/tamper-receipts/` with a manifest. The receipt for 30 comes from FreeTSA and the one for 40 from
  DigiCert. The battery never requests receipts; it refuses a stored receipt whose request no longer matches the
  recomputed row.
- **T6b timestamps:** rows 25..50 get `base + (seq − 25) × 150 ms`, with the base time stored in the manifest
  (three seconds before the requests).
- **X2:** the tester's root (RSA 2048) and pinned signer (P-256) are generated at run time and never stored. Each
  token's genTime is the row's whole second plus one second, and the nonce is fixed, so the output is
  deterministic.
- **ANCHOR_TIME lines** in expected outputs are derived from the bytes of the frozen or replaced receipts.

### Spec 005 — Interceptor and overhead (M3) (Blueprint §2, §5.4, §7 (M3))

- **Commit boundary for `epistemic_pause` and `human_resolution`:** the same as for `tool_call`; the agent
  does not continue until the COMMIT is confirmed, and an unknown outcome stops it.
- **`result_digest` when a tool fails:** `result_json_value` is the JSON object
  `{"error_type": <error_type>, "message": <error message as a JSON string>}`, hashed under §4.4.
- **Reference agent:** a minimal scripted agent in TypeScript, with no framework and no LLM, that calls three
  deterministic local tools. One of them always fails, to exercise `result_digest` with an error.
- **M3 workload:** 100 events per run, measured with and without the interceptor; the measured latency is
  reported. If time runs short in this work package, Cut 1 of §8 applies and M3 is reported as unmeasured.
- **Pepper encoding:** `TEAR_HMAC_PEPPER` holds lowercase hex of at least 64 characters (32 bytes). The
  writer decodes it to bytes and rejects any other format.
- **Writer start-up:** the provisional rule of this work package (the writer accepted events only in the
  session that created the chain) was retired by spec 006. The interceptor now starts through `initializeChain`
  and then the full §5.6 writer start-up under fresh exclusion, so it also continues an existing chain.
- **Start-up order:** `Interceptor.start` reads and checks `TEAR_HMAC_PEPPER` first, so a missing or invalid
  value writes nothing (not even `.writer.lock`); then `initializeChain`, then `ChainWriter.open`. Only the public
  `pepper_id` is recorded, in the genesis row.
- **Operation literals:** `tool_call` and `tool_result` use `execute_tool`, `agent_final_response` uses
  `invoke_agent`, `epistemic_pause` uses `tear.epistemic_pause`, and `human_resolution` uses
  `tear.human_resolution`.
- **Adapter JSON domain:** null, booleans, finite numbers, well-formed strings, dense arrays and plain objects with
  data properties. Anything else (undefined, NaN, BigInt, functions, symbols, Date, Map, class instances, getters,
  cycles, lone surrogates) is `ADAPTER_JSON_INVALID`. U+0000 is allowed in transient arguments, which are not
  persisted (§4.4).
- **A tool that throws something other than `ToolError`:** an adapter fault, not a tool result. No `tool_result`
  is recorded and nothing is delivered, so the call stays visible as `INCOMPLETE_EXECUTION`. The same holds for a
  tool result outside the JSON domain.
- **`tool_result.summary`:** `<tool> succeeded` or `<tool> failed: <error_type>`.
- **M3 per-event latency:** a tool step counts as two events: the call half (recording `tool_call`) and the result
  half (running the tool, then recording `tool_result`). Pauses, resolutions and final answers count as one event
  each. Without the interceptor the same halves are timed with no recording. The median is taken over every
  ordinary event of the 5 runs.
- **M3 anchor points:** each measured run is a new chain of its own with `max_auto_anchor_seq = 20` (anchors at 10
  and 20): 10 samples over 5 runs, the fewest that give a p95, reported as nearest-rank p50 and p95. One
  unmeasured warm-up run (no anchors) precedes the measured runs.
- **M3 record size:** the mean byte length of an exported `events.jsonl` row, final LF included.
- **M3 cost:** reported as an absolute time per ordinary event (median with minus median without), never as a
  ratio: the scripted tools are trivial, so the baseline is close to zero by construction.
- **M3 output:** `npm run m3` writes `test-results/m3-results.md` and the raw samples to `m3-results.json`;
  `npm run m3:render` re-renders the table from the JSON without measuring again. CI does not run M3.

### Spec 006 — Recovery, close and evidence package (Blueprint §5.6, §5.8, §5.3 (evidence package for offline verification), §8 (Cut 2 and Cut 3 profiles))

- **Where reconciliation runs:** inside `ChainWriter.open`, under the writer's own exclusion, after full validation
  (§5.6 step 1) and before the writer is returned. A start-up that fails releases writerConn and flock; a failed
  namespace mutation also runs drain-and-exit (§5.5).
- **Classifier:** `src/recovery/classifier.ts`, behind the spec 001 interface, used by both `initializeChain`
  inspection and writer start-up. It validates packages with the verifier's Step 2 checks
  (`src/verify/anchors.ts`), so the recoverer is the second consumer of the receipt checks (spec 003 AC-22).
  Step 3 contradictions and missing committed evidence are reported as inconsistent before a state is chosen.
- **E2 condition ("confirmed"):** the single `.tsq` is resolved when row m+1 is committed in SQL as a
  `checkpoint_failed(target_seq = m)`, or as a `checkpoint_anchored(anchored_seq = m)` whose package m is confirmed
  valid. A `.tsq` whose anchored control has no valid package never reaches E2: step 3 fails first on missing
  confirmed evidence.
- **E4 "valid package":** package k passes the full Step 2 (2.1–2.7, temporal predicate included) against the
  committed log, and the control at k+1 agrees with it in `tsr_sha256` and `tsa_gen_time`.
- **After a repair:** the state row is reloaded on writerConn and the view is classified again; anything other than
  a clean E1 (no pending anchor, no `.tmp` or `.tsq`) fails `RECONCILIATION_STATE_INCONSISTENT`.
- **Start-up directory barrier:** run through the same guarded file queue as every namespace mutation, so it
  fails closed under the same rules.
- **E8:** after the residue is deleted, the TSA flow runs again with a fresh nonce, from the same queue slot; its
  outcome (anchored or `checkpoint_failed`) resolves the pending anchor.
- **`closeChain` result:** `{ result, branch }`, plus the anchor outcome when a TSA was contacted. Sealing is its own
  durable transaction; a pending close anchor uses `pending_mode` `close` (B2) or `close_retry` (B3).
- **Cut profiles:** from Cut 2 on, B3 is retired (a retry request returns `UNANCHORED_FAILURE` without contacting a
  TSA) and B1 always returns `ANCHORED_FIRST_ATTEMPT`. From Cut 3 on, any `.tmp`, `.tsq` or pending anchor fails
  start-up and nothing is deleted.
- **Evidence package:** `buildEvidencePackage` copies complete pairs (read without following symlinks), then
  exports with the read-only exporter. It refuses an existing output directory.
- **Bundle at inspection:** `initializeChain` loads the requested bundle to validate existing packages; a bundle
  that fails loading stops inspection with `TSA_BUNDLE_UNLOADABLE`.

### Spec 008 — Durable file primitives (Blueprint §5.5)

- **Mutation queue:** each writer generation owns one `DurableNamespace`, whose strict FIFO queue carries every
  file mutation of the chain and tracks it until it settles. Chain operations that publish or delete (anchoring,
  recovery, close) await these mutations from inside their own slot of the chain's operation queue, so the two
  queues never interleave work for one chain. §5.3 requires every file mutation of a chain to share one strict
  serial queue; it does not require that queue to be the chain's operation queue.
- **Guard checks:** the guard is checked before each operation starts and again before each mutating system call
  inside it. An invalidation observed mid-operation stops it there, with no cleanup.
- **Entry names:** a mutation accepts only a plain entry name inside the namespace and never `.writer.lock`; an
  invalid name is rejected before any system call and is not a mutation failure.
- **Fail-stop:** a failed mutation invalidates the guard, refuses all later work, and calls the owner's
  drain-and-exit handler once, after everything already queued has settled.

## 11. Trust surfaces of this implementation

- A mandatory statement that the ASN.1 DER reader is written in this repository and is a trust surface of its own: tested with negative vectors for every rejection rule and checked against `openssl` on every real receipt and certificate, with no external review.
- The writer lock uses `fs-ext@2.1.1`, a native addon compiled at install time, because Node.js does not expose
  `flock(2)` (§5.3). Its install script is the only one approved in `package.json`; the offline verifier does not
  load it.
